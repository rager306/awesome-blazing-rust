# Awesome Blazing Rust [![Awesome](https://awesome.re/badge.svg)](https://awesome.re)

> A catalog of Rust projects where every speed claim is traced to a measurement: who ran it, on what hardware, against what baseline, and where the advantage stops. Architecture patterns are named; entries without a traceable claim are tagged as case studies.

**The rule: every speed claim must name its source.** Entries with a traceable measurement are tagged `measured`; architectural insights and tools are tagged `case-study` or `tool`. Projects without a public benchmark live in the Candidates section until they show evidence. Each entry carries a `Blazing:` line (the measurement), a `Measured by:` line (who ran it) and an `Arch:` line (the patterns - indexed in [PATTERNS.md](PATTERNS.md)).

**Why this list exists.** "Blazingly fast" became a meme before it became a claim: there is a GitHub topic for it, a satirical awesome-list, and a README line that means "written in Rust" more often than it means "measured". This catalog is the counter-move - the same projects, but only with a number, a baseline, a named measurer and a link to the method. A card without those is a case study, not a measurement.

## Hall of Fame

The canonical blazing projects - the ones that made "Rust is fast" a meme with receipts.

- [ripgrep](https://github.com/BurntSushi/ripgrep) - recursive grep with regex support. **Blazing:** repeatedly benchmarks 10×+ faster than GNU grep on large trees (see the project's own fgrep/grep comparisons in the [GUIDE](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md#benchmarks)). **Measured by:** author. **Type:** measured. **Arch:** `simd`, `lock-free-parallel-walk`, `zero-copy`.
- [memchr](https://github.com/BurntSushi/memchr) - substring & multi-substring search. **Blazing:** SIMD-accelerated; the backbone under `regex` and `ripgrep`. **Type:** case-study. **Arch:** `simd`, `branchless`.
- [regex](https://github.com/rust-lang/regex) - the regex engine. **Blazing:** literal optimizations + SIMD-powered DFA; its docs document multi-x speedups vs naive engines. **Type:** case-study. **Arch:** `automata-compilation`, `simd`, `prefilter`.
- [tokio](https://github.com/tokio-rs/tokio) - the async runtime most of this list runs on. **Blazing:** work-stealing scheduler; powers production at AWS, Microsoft, Discord. **Type:** case-study. **Arch:** `work-stealing`, `io-driver`.
- [hyperfine](https://github.com/sharkdp/hyperfine) - command-line benchmarking tool. **Blazing:** statistical warm-up/outlier analysis in a CLI; the tool we benchmark this list with. **Type:** tool. **Arch:** `statistical-rigor`.

## Algorithms & Data Structures

- [sux](https://github.com/vigna/sux-rs) - succinct structures: Elias-Fano, rank/select, static functions, minimal perfect hashing. **Blazing:** scales to trillions of keys with very fast queries executed directly on the compressed representation. **Type:** case-study. **Arch:** `succinct`, `rank-select`, `zero-copy`.
- [roaring-rs](https://github.com/RoaringBitmap/roaring-rs) - Roaring compressed bitmaps for IDs, postings and set operations. **Blazing:** own run, v2 methodology (2026-10, quiet 2-vCPU, median of 7): dense union materialize 2.5 ms vs 1879 ms for HashSet (755x) and intersect 12.6 ms vs 1176 ms (93x); at sparse 0.02-0.2% density materialize wins only 4-16x, contains is 6-11x slower than HashSet, and BTreeSet wins count-only scans - density and op semantics decide ([full run](https://github.com/rager306/awesome-blazing-rust/blob/main/runs/roaring-2026-10/RESULTS.md), scope: component). **Measured by:** catalog. **Type:** measured. **Arch:** `bitmap-index`, `density-dependent`.

Well-known algorithms, implemented properly in Rust.

### Collections

- [hashbrown](https://github.com/rust-lang/hashbrown) - SwissTable hash map; the implementation inside Rust's std since 1.36. **Blazing:** open addressing with SIMD control-byte probing. **Type:** case-study. **Arch:** `simd`, `cache-conscious-layout`.
- [indexmap](https://github.com/indexmap-rs/indexmap) - insertion-ordered hash map + set, O(1) amortized with order. **Blazing:** std-level speed with deterministic iteration. **Type:** case-study. **Arch:** `compact-index`.
- [im](https://github.com/bodil/im-rs) - immutable/persistent collections with structural sharing (archived 2026 - historical entry). **Blazing:** O(1) clones - cheap snapshots for concurrent and functional workloads. **Type:** case-study. **Arch:** `structural-sharing`, `hamt`.
- [smallvec](https://github.com/servo/rust-smallvec) - stack-allocated small vectors. **Blazing:** eliminates heap allocation for the common short case. **Type:** case-study. **Arch:** `inline-storage`.
- [itertools](https://github.com/rust-itertools/itertools) - the algorithm toolbox on iterators. **Blazing:** zero-cost abstractions, fused adapters. **Type:** tool. **Arch:** `zero-copy`.

### Hashing & Checksums

- [blake3](https://github.com/BLAKE3-team/BLAKE3) - cryptographic hash. **Blazing:** ~GB/s on modern x86 (AVX2/AVX-512, per the [project's benchmark table](https://github.com/BLAKE3-team/BLAKE3#benchmarks)); orders above SHA-2/SHA-3. **Measured by:** author. **Type:** measured. **Arch:** `simd`, `merkle-tree`, `multi-core-hash`.
- [xxhash-rust](https://github.com/DoumanAsh/xxhash-rust) - xxHash (XXH3). **Blazing:** non-crypto hashing at memory-bandwidth speeds. **Type:** case-study. **Arch:** `simd`.
- [ahash](https://github.com/tkaitchuck/aHash) - DoS-resistant fast hash map hasher. **Blazing:** documented multi-fold wins over SipHash on hash-map workloads. **Type:** case-study. **Arch:** `aes-ni`.
- [crc32fast](https://github.com/srijs/rust-crc32fast) - CRC-32. **Blazing:** 15× faster than naive, via slicing-by-8 and SIMD switching ([crate docs](https://github.com/srijs/rust-crc32fast#performance)). **Measured by:** author. **Type:** measured. **Arch:** `simd`, `table-driven`.

### Pathfinding & Spatial

- [pathfinding](https://github.com/samueltardieu/pathfinding) - BFS, Dijkstra, A*, K-means, CSPs and friends. **Blazing:** the Swiss-army graph-algorithms crate. **Type:** tool. **Arch:** `generic-vertices`.
- [rstar](https://github.com/Stoeoef/rstar) - R*-tree spatial index. **Blazing:** bulk-loaded queries at interactive rates. **Type:** case-study. **Arch:** `bulk-loading`.

### Math & Parallel

- [num-bigint](https://github.com/rust-num/num-bigint) - arbitrary-precision integers. **Blazing:** Karatsuba multiplication in the num-rational stack. **Type:** case-study. **Arch:** `classical-algorithms`.
- [rayon](https://github.com/rayon-rs/rayon) - data parallelism. **Blazing:** near-linear scaling on parallel sort/map in typical workloads. **Type:** case-study. **Arch:** `work-stealing`, `join-split`.

### Compression

- [lz4_flex](https://github.com/pseitz/lz4_flex) - pure-Rust LZ4. **Blazing:** no C dependency; the safe configuration avoids `unsafe` and is benchmarked separately from the unsafe-feature build. **Type:** case-study. **Arch:** `pure-rust-port`, `feature-gated-safety`.
- [zstd-safe](https://github.com/gyscos/zstd-rs) - zstd bindings. **Blazing:** the ratio/speed king of general compression, one call away. **Type:** case-study. **Arch:** `c-binding`.

## Concurrency & Lock-free

- [bbtree](https://github.com/XiangpengHao/bbtree) - concurrent ordered map built from a cost model. **Blazing:** 5× vs std `BTreeMap` at 1 thread; 12× vs crossbeam-skiplist at 96 threads; map-only swap into fjall/SlateDB/Tonbo/Turso/Lance: 1.16-6.83× end-to-end; p99 5× lower ([design post and benchmark tables](https://github.com/XiangpengHao/bbtree#benchmarks)). **Measured by:** author. **Type:** measured. **Arch:** `cost-model-driven`, `simd`, `versioned-locks`, `inline-keys`, `prefix-keys`, `verus-in-ci`, `shuttle-in-ci`.
- [crossbeam](https://github.com/crossbeam-rs/crossbeam) - epoch-based memory reclamation + concurrent queues/deques. **Blazing:** the substrate half of modern lock-free Rust runs on. **Type:** case-study. **Arch:** `epoch-reclamation`, `lock-free`.
- [dashmap](https://github.com/xacrimon/dashmap) - concurrent hash map. **Blazing:** sharded locking beats global `RwLock<HashMap>` by design. **Type:** case-study. **Arch:** `sharding`.
- [papaya](https://github.com/ibraheemdev/papaya) - concurrent hash map, read-optimized counterpoint to sharded designs. **Blazing:** built around read throughput with incremental resizing. **Type:** case-study. **Arch:** `read-optimized`, `hyaline-reclamation`.

- [monoio](https://github.com/bytedance/monoio) - ByteDance's thread-per-core runtime. **Blazing:** io_uring-first, production at scale. **Type:** case-study. **Arch:** `thread-per-core`, `io-uring`.
- [io-uring](https://github.com/tokio-rs/io-uring) - raw io_uring bindings. **Blazing:** one syscall for many ops - the kernel interface built to be ignored by no one. **Type:** case-study. **Arch:** `io-uring`, `batching`.

## Storage & Embedded Databases

- [fjall](https://github.com/fjall-rs/fjall) - LSM storage engine. **Blazing:** benchmarked against rocksdb/sled with open methodology; bbtree swap-in partner. **Type:** case-study. **Arch:** `lsm`, `partitioned`.
- [SlateDB](https://github.com/slatedb/slatedb) - LSM on object storage (S3/R2). **Blazing:** cloud-native LSM; bbtree e2e partner. **Type:** case-study. **Arch:** `lsm`, `object-storage`.
- [sled](https://github.com/spacejam/sled) - the famous beta embedded DB. **Blazing:** the project that set the tone for "blazing" claims - treat numbers as historical. **Type:** case-study. **Arch:** `lsm-plus-btree`.

- [oxigraph](https://github.com/oxigraph/oxigraph) - RDF/SPARQL store. **Blazing:** embedded+server SPARQL with active perf discipline; persistence is RocksDB-backed by default (feature-gated in-memory alternative). **Type:** case-study. **Arch:** `sparql-engine`, `storage-backend-flag`.
- [cozo](https://github.com/cozodb/cozo) - embedded Datalog graph DB. **Blazing:** recursive queries as a first-class, stored-procedure-free primitive. **Type:** case-study. **Arch:** `datalog`, `embedded`.

## Search & Text Processing

- [fst](https://github.com/BurntSushi/fst) - finite state transducers for large sets and maps with streaming construction. **Blazing:** ~16,000,000 Wikipedia article titles (384 MB of strings) compress to a 157 MB fst with fast prefix/fuzzy queries (author's 2015 measurement - historical, tied to that setup). **Type:** case-study. **Arch:** `finite-state-transducer`, `compact-serialization`.

- [tantivy](https://github.com/quickwit-oss/tantivy) - full-text search engine. **Blazing:** benchmarked against Lucene, frequently ahead on ingest. **Type:** case-study. **Arch:** `inverted-index`, `columnar`.
- [aho-corasick](https://github.com/BurntSushi/aho-corasick) - multi-pattern matching. **Blazing:** the prefilter behind regex/ripgrep multi-literal search. **Type:** case-study. **Arch:** `automata-compilation`, `simd`.
- [winnow](https://github.com/winnow-rs/winnow) - parser combinators. **Blazing:** zero-copy parsing as the default path. **Type:** case-study. **Arch:** `zero-copy`, `combinators`.

## Data & Analytics

- [sonic-rs](https://github.com/cloudwego/sonic-rs) - SIMD JSON parsing straight into serde-compatible structs (no intermediate tape re-parse). **Blazing:** published benchmarks vs serde_json and simd-json; the `sanitize` feature needed for LLVM sanitizers costs ~30% in serialization - production builds keep it off ([benchmarks](https://github.com/cloudwego/sonic-rs#performance)). **Measured by:** author. **Type:** measured. **Arch:** `simd`, `typed-parse-direct`.
- [simd-json](https://github.com/simd-lite/simd-json) - SIMD JSON parsing into a tape, following the simdjson design in Rust. **Blazing:** performance tracks the C++ simdjson implementation; best numbers require a custom allocator (mimalloc/jemalloc). **Type:** case-study. **Arch:** `simd`, `tape-representation`.

- [polars](https://github.com/pola-rs/polars) - DataFrames. **Blazing:** documented multi-x wins over pandas on groupby/join; query-optimized, lazy, parallel. **Type:** case-study. **Arch:** `columnar`, `query-optimization`, `simd`.
- [apache-arrow-rs](https://github.com/apache/arrow-rs) - Arrow columnar format. **Blazing:** zero-copy interchange - the "no-serialization" tax advantage. **Type:** case-study. **Arch:** `columnar`, `zero-copy`, `stringview`.
- [datafusion](https://github.com/apache/datafusion) - extensible, Arrow-native SQL query engine for single-node analytics - the engine many Rust data systems embed. **Blazing:** DataFusion 43.0.0 posted the fastest single-node Parquet numbers on ClickBench "hot" runs (2024-11-16, partitioned 14 GB Parquet, c6a.4xlarge 16 CPU / 32 GB) - ahead of DuckDB, chDB and ClickHouse on identical hardware, the first Rust engine to hold first place; over 30% faster than DataFusion 34 (Dec 2023) on the same suite, while the authors concede DuckDB stays slightly ahead on "cold" runs ([post](https://datafusion.apache.org/blog/2024/11/18/datafusion-fastest-single-node-parquet-clickbench/), scope: component; [bench scripts](https://github.com/ClickHouse/ClickBench/tree/main/datafusion), [raw data](https://github.com/apache/datafusion/issues/13099)). **Measured by:** third-party. **Type:** measured. **Arch:** `query-optimization`, `columnar`, `stringview`, `extensible`.

## Caching & Working Set

The win here is avoiding expensive misses - judge these by hit ratio on realistic admission policies, not by single-get latency.

- [moka](https://github.com/moka-rs/moka) - concurrent cache, Rust port of Caffeine ideas: admission/eviction policies, sync and async APIs. **Blazing:** the leverage is Window-TinyLFU admission keeping hot keys resident; hit-ratio studies are published in the wiki. **Type:** case-study. **Arch:** `window-tinylfu`, `hit-ratio-first`.
- [foyer](https://github.com/foyer-rs/foyer) - hybrid RAM + disk cache for data-intensive systems. **Blazing:** eviction-policy benchmark harness (hit-ratio benches) lives in the repo - policy choice is measured, not vibes. **Type:** case-study. **Arch:** `hybrid-cache`, `hit-ratio-first`.

## Incremental Computation

Recompute nothing you can update: define the computation once, respond to changes.

- [differential-dataflow](https://github.com/TimelyDataflow/differential-dataflow) - incremental data-parallel computation on timely dataflow. **Blazing:** in the author's graph example (10M nodes, 50M edges), a 15 s initial computation answers input changes in ~230 us - about 100,000x faster than recomputing; batched updates average ~5 us each; two workers cut the build from 15 s to ~8 s ([experiments](https://github.com/TimelyDataflow/differential-dataflow/tree/master/experiments)). **Measured by:** author. **Type:** measured. **Arch:** `incremental-view-maintenance`, `arrangement-indexing`, `data-parallel`.

- [molar](https://github.com/yesint/molar) - memory-safe molecular-dynamics trajectory analysis and modeling library in Rust (successor of the C++ Pteros library), with Python bindings. **Blazing:** a peer-reviewed paper reports it outperforming popular molecular analysis libraries, but the numbers live in the paper's tables, not the repo README; baselines and per-task figures unverified by us ([J Comput Chem 2025;46(1):e27536](https://doi.org/10.1002/jcc.27536)). **Type:** case-study. **Arch:** `data-parallel`, `python-bridge`.
- [solar](https://github.com/paradigmxyz/solar) - modular Solidity compiler in Rust, a drop-in compile-time replacement for solc workloads (ABI, bytecode, IR). **Blazing:** ~40x faster than solc at generating ABI in the repo's hyperfine benchmark, and the Paradigm launch post reports >41x vs solc on Solady's ABI; a compile-time/gas/size suite against solc (legacy and via-IR pipelines), slang and oksolc runs in CI with methodology in [benches/runtime/README.md](https://github.com/paradigmxyz/solar/blob/main/benches/runtime/README.md). **Measured by:** author. **Type:** measured. **Arch:** `pure-rust-port`, `statistical-rigor`.
- [zero-pool](https://github.com/void-research/zero-pool) - std-only, lock-free FIFO MPMC thread pool: one global queue instead of per-worker queues, function-pointer dispatch, and tasks write results straight into caller-provided memory instead of sending them through channels. **Blazing:** the submitting issue cites a criterion table (AMD 5900X, Linux) of 458,742 ns vs rayon 782,252 ns on individual tasks (1.7x) and 4.49 ms vs 4.87 ms on heavy compute, honestly losing on per-task overhead (32.8 us vs 30.1 us), but no benchmark section was found in the README fetched 2026-11-13 - numbers unverified; only the [Miri verification report](https://github.com/void-research/zero-pool/blob/main/tests/README.md) checked out. **Type:** case-study. **Arch:** `lock-free`.
- [apache/iggy](https://github.com/apache/iggy) - Apache message streaming platform (Kafka-style pub/sub server) rebuilt on a thread-per-core shared-nothing architecture over io_uring via the compio runtime. **Blazing:** at a matched ~1,000 MB/s per node write load, v0.7.0 (thread-per-core) vs v0.5.0 (tokio) cut p99 tail latency 4.52→1.82 ms at 32 producers/32 streams, and with fsync-per-batch raised throughput 931→1,102 MB/s per node while halving p95; consumer reads reached 3,361 MB/s on 16 consumers (full percentile tables per run in the [migration post](https://iggy.apache.org/blogs/2026/02/27/thread-per-core-io_uring/), every run published at benchmarks.iggy.apache.org). **Measured by:** author. **Type:** measured. **Arch:** `thread-per-core`, `io-uring`, `sharding`, `batching`.
- [alyze](https://github.com/turbopuffer/alyze) - UAX #29-compliant word/sentence tokenizer and full-text analysis pipeline (lowercasing, ASCII folding, English stemming, stopword removal) built on a hand-rolled DFA (MIT, in production at turbopuffer as the word_v4 tokenizer, active: last push 2026-10-28). **Blazing:** over 64 MiB of English Wikipedia text, author's `cargo bench` (M5 Pro, median of 16 samples, [benchmarks](https://github.com/turbopuffer/alyze#benchmarks), repro `cargo bench --bench wikipedia`): word break 508 MiB/s, sentence break 465 MiB/s, tokenize-only analysis 415 MiB/s falling to 126 MiB/s for the full pipeline - the per-stage table shows stemming is the costly step (283 → 132 MiB/s); no external tokenizer baseline is named, so this is absolute throughput, not a win over a competitor. **Type:** case-study. **Arch:** `automata-compilation`. *Needs: a named-baseline comparison (e.g. vs unicode-segmentation) to promote to measured.*
- [wordchipper](https://github.com/zspacelabs/wordchipper) - BPE tokenizer for the OpenAI GPT-2-family vocabularies (r50k/cl100k/o200k) with swappable internals (compile-time logos DFA, runtime regex-automata, fancy-regex lexers behind one API), parallel encode, Python/WASM bindings and a no_std core; alpha (0.7), 37 stars, with a self-published performance paper. **Blazing:** author benchmark on a 64-core AMD 3990X: 1.7 GiB/s (default regex-automata) and 2.7 GiB/s (logos DFA) on r50k encode vs tiktoken-rs 386 MiB/s and HuggingFace tokenizers 49.7 MiB/s (o200k: 1.5/2.4 GiB/s vs 265 MiB/s) - claimed 4.3-5.7x (regex) and 6.9-9.2x (DFA) over tiktoken-rs, 2-4x via Python; DFA-lexer output verified byte-identical to the regex reference over ~594M generated codepoint tuples ([paper](https://zspacelabs.ai/wordchipper/articles/substitutable/), [table](https://github.com/zspacelabs/wordchipper#encode-side-by-side-benchmarks)). **Measured by:** author. **Type:** measured. **Arch:** `automata-compilation`, `data-parallel`, `no-std-friendly`.
- [fastdedup](https://github.com/wapplewhite4/fastdedup) - single-machine CLI that strips exact and near-duplicate documents from ML training datasets (JSONL, gzip, Parquet) with a Bloom-filter hash pass and a MinHash + LSH pass. **Blazing:** on FineWeb sample-10BT (14.8M records, 29 GB, one Hetzner CCX43) exact dedup took 2m55s with 688 MB peak RAM on one core vs 7m55s and 21.9 GB for a DuckDB + SHA-256 baseline on 4+ cores (2.7x, both found exactly 51,392 duplicates); fuzzy MinHash dedup finished in 36m44s while the datatrove reference baseline, run locally with 1 task, was killed at 3h50m still in stage 1 - with the honest trade-off that fastdedup holds a 23 GB in-memory LSH index where datatrove spills to disk at 1.1 GB ([methodology + reproduce scripts](https://github.com/wapplewhite4/fastdedup/blob/main/benchmarks/README.md)). **Measured by:** author. **Type:** measured. **Arch:** `aes-ni`, `columnar`.
- [lionturtle](https://github.com/danthegoodman1/lionturtle) - embedded Rust key-value store built on TurtleKV's Bε-tree TurtleTree with SILK-paced checkpoints and C/C++ bindings. **Blazing:** YCSB on 50M×128B records, LZ4, 16 threads: update/insert p99.9 5–15× below RocksDB (YCSB-A update p99.9 30 µs vs 456 µs RocksDB / 347 µs fjall), throughput 1.05–1.70× RocksDB on every workload, 5.8 vs 7.7 (RocksDB) / 9.3 (fjall) bytes written per user byte, and at 150k durable ops/s read p99 0.37 ms vs 860 ms RocksDB - setup and reproduce commands in [BENCHMARKS.md](https://github.com/danthegoodman1/lionturtle/blob/main/BENCHMARKS.md). **Measured by:** author. **Type:** measured. **Arch:** `c-binding`, `batching`.
- [radixox](https://github.com/JoshuaBOUCHAT/radixox) - Redis/Valkey-protocol in-memory key-value store: keys ordered in an adaptive radix tree, hand-written io_uring loop on one serving thread, libc-free static binary, plus prefix-pruned SCAN and KRANGE pagination Redis lacks. **Blazing:** 311,910 ops/s unpipelined and 3.08M pipelined (depth 32) on 1 core vs Valkey 9.1.2's 190,864 / 2.15M, prefix `SCAN` 4 ms vs 121 ms over 1M keys — loopback, memtier 2.4.2, 1M×100-byte keys, one run per point, reproducible via `scripts/readme_bench.sh` ([methodology](https://github.com/JoshuaBOUCHAT/radixox#benchmarks)); discloses its losses (`appendfsync always` on one connection: Valkey +64%, BGSAVE p99.99 1.21 ms vs 0.88 ms). **Measured by:** author. **Type:** measured. **Arch:** `io-uring`, `thread-per-core`, `prefix-keys`, `cache-conscious-layout`.
- [gzippy](https://github.com/JackDanger/gzippy) - drop-in parallel gzip/gunzip CLI writing standard RFC 1952 output any decompressor reads. **Blazing:** author benchmark on the 202 MB Silesia corpus (Apple M4 Pro 14 cores, level 6, median of 15 runs): compression ~700 MB/s vs pigz ~150 MB/s (~4.7x) and Apple gzip ~40 MB/s (~17x); decompression ~930 MB/s ≈ par with Apple gzip ~900 MB/s ([methodology](https://github.com/JackDanger/gzippy#how-fast), reproduce via scripts/readme_benchmark.py). **Measured by:** author. **Type:** measured. **Arch:** `data-parallel`, `zero-copy`.
- [NumKong](https://github.com/ashvardanian/NumKong) - mixed-precision BLAS-like kernels (dot products, distances, GEMM) for 17 numeric types from 4-bit integers to 128-bit complex, 2,000+ SIMD kernels across x86/Arm/RISC-V/WASM with Rust bindings over a C core. **Blazing:** single-threaded 2048-d dot on Intel Sapphire Rapids: i8 14.8 gso/s vs NumPy 2.4 + OpenBLAS 1.1 gso/s (~13x, lower error via wider accumulators); methodology in the companion [NumWars](https://github.com/ashvardanian/NumWars) Criterion suite (packed i8 dots 2,783 vs nalgebra 118.7 GSO/s on Apple M5 Pro, different precisions); loses on f32 matmul, 37.7 vs MKL 145 gso/s. **Measured by:** author. **Type:** measured. **Arch:** `simd`, `runtime-dispatch`, `kernel-fusion`, `c-binding`.
- [flock](https://github.com/succinctlabs/flock) - zero-knowledge prover/verifier for R1CS circuits over the binary field F_2^128 (zerocheck+lincheck PIOP, Ligerito multilinear PCS), with hand-tuned AVX-512/VPCLMULQDQ and NEON field kernels. **Blazing:** proves 305.3k SHA-256 and 629.8k BLAKE3 compression functions/s at batch 262144 on a 32-core Threadripper 7970X (9.9x and 9.7x its own 1-thread runs), and 497.9k / 957.7k on a 10-core Apple M4 Max; best-of-3 with verified warm-up, reproducible per [BENCHMARKS.md](https://github.com/succinctlabs/flock/blob/main/benchmarks/BENCHMARKS.md), which also scripts head-to-head runs against binius64/plonky3/hashcaster. **Measured by:** author. **Type:** measured. **Arch:** `simd`, `finite-fields`, `recursive-proofs`, `data-parallel`.
- [rust-tango](https://github.com/0xfinetuned/rust-tango) - lock-free, zero-copy single-producer/single-consumer channel ported from Firedancer's Tango IPC subsystem, with credit-based backpressure and `no_std` support. **Blazing:** 26.6 M msg/s on 64-byte payloads vs crossbeam-channel 7.3 M (3.6×), ringbuf 10.7 M, std mpsc ~9 M; 12.4 GiB/s on 1 KiB payloads vs crossbeam 6.9 GiB/s (1.8×); 90 µs ping-pong vs crossbeam 105 µs — Apple M3 Pro, 1000 criterion samples per run, rerunnable via `cargo bench` ([benchmark source](https://github.com/0xfinetuned/rust-tango/blob/main/benches/channel_comparison.rs)). **Measured by:** author. **Type:** measured. **Arch:** `lock-free`, `zero-copy`, `pure-rust-port`, `cache-conscious-layout`, `no-std-friendly`.
- [ForkUnion](https://github.com/ashvardanian/fork_union) - NUMA-aware fork-join thread pool for tight `parallel for`-style loops, a C++17 core with a first-class Rust crate (`forkunion`) that wraps it and adds a Rust-only Rayon-style iterator layer (Apache-2.0, active, 383 stars, v3.0.4). **Blazing:** author benchmark on 4 machines (Apple M5 Pro, Intel RPL, 128-core Intel SPR, 192-core Graviton 5) with bit-identical workloads and matched `-O3`+`target-cpu=native` flags, full tables in the [README Performance section](https://github.com/ashvardanian/fork_union#performance) and [methodology post](https://ashvardanian.com/posts/beyond-openmp-in-cpp-rust/): on the 128-core SPR box the Rust crate dispatches an N-body step in 40 µs (static) vs 483 µs for Rayon, and traverses 65.2 GTEPS on connected components vs Rayon's 8.5 (~7.7×; 258.7 vs 8.4 on Graviton 5); headline claim ~3-6× vs OpenMP and ~12-16× vs Rayon/Taskflow on per-loop dispatch — but Rayon wins connected components on the 18-core M5 Pro (23.8 vs 19.4) and 24-core RPL box (9.4 vs 5.2), so the advantage is core-count-dependent. **Measured by:** author. **Type:** measured. **Arch:** `lock-free`, `cache-conscious-layout`, `data-parallel`, `c-binding`.
- [spargio](https://github.com/soumyarupsarkar/spargio) - self-described experimental work-stealing io_uring async runtime that hybridizes thread-per-core sharding with pre-execution work stealing, coordinating shards via io_uring msg_ring messages. **Blazing:** Criterion mean latencies, 3.8x vs tokio on steady ping-pong RTT (367 µs vs 1.409 ms) and 1.7x vs compio on rotating-hotspot network loads (11.0 ms vs 18.8 ms), while reporting compio ~70% faster on sustained balanced throughput ([benchmark tables](https://github.com/soumyarupsarkar/spargio#benchmark-results)). **Measured by:** author. **Type:** measured. **Arch:** `io-uring`, `work-stealing`, `sharding`.
- [pgvectorscale](https://github.com/timescale/pgvectorscale) - Postgres extension written in Rust (PGRX) adding StreamingDiskANN disk-based graph indexes and Statistical Binary Quantization compression on top of pgvector. **Blazing:** 28x lower p95 latency and 16x higher query throughput than Pinecone's storage-optimized s1 index at 99% recall on 50M Cohere 768-dim embeddings, 1.4x/1.5x vs Pinecone's performance-optimized p2 at 90% recall, at ~25% of the monthly cost self-hosted on EC2 ([methodology](https://www.timescale.com/blog/pgvector-vs-pinecone/)) - baseline is a managed competitor (June 2024, PostgreSQL 16.3, pgvector 0.7.0), not pgvector itself. **Measured by:** author. **Type:** measured. **Arch:** `quantization`, `quality-vs-speed`.
- [vortex](https://github.com/vortex-data/vortex) - Rust columnar file format and compression toolkit (LF AI & Data incubation, Apache-2.0) that stores analytics tables with pluggable per-column encodings as a Parquet alternative. **Blazing:** the project's continuous benchmark site [bench.vortex.dev](https://bench.vortex.dev) shows scan 28.1x Parquet geomean (77.8 vs 3.2 GB/s aggregate), writes 2.8x (1671 vs 605 MB/s), and ClickBench geomean 4.33 s vs 5.76 s for the same DataFusion engine on Parquet, at ~Parquet-equal size (1.03x mean); methodology is public and re-runnable via the in-repo vx-bench/bench-orchestrator, but wins are engine-pairing specific — on NVMe TPC-H plain DuckDB on its own format still beat DuckDB-on-Vortex. **Measured by:** author. **Type:** measured. **Arch:** `columnar`, `extensible`, `zero-copy`.
- [emdb](https://github.com/jamesgober/emdb-rs) - Bitcask-style embedded key-value store: append-only journal, sharded hash index, lock-free reads, group-commit fsync. **Blazing:** author-run 5M-record mirror of redb's published workload ([docs/BENCH.md](https://github.com/jamesgober/emdb-rs/blob/main/docs/BENCH.md)): bulk load 13,724ms vs redb 2.6's 43,660ms (3.2x), batch writes 20.4x, 8-thread random reads 511ms vs 13,026ms (25.5x, ~9.78M reads/sec) — wins every column; single Windows 11 NVMe machine, v0.9.0 baseline dated 2026-05-04. **Measured by:** author. **Type:** measured. **Arch:** `lock-free`, `sharding`, `batching`.
- [redistill](https://github.com/redistill-io/redistill) - Redis-compatible in-memory key-value store in Rust (Tokio + sharded DashMap, RESP, optional RDB/AOF persistence). **Blazing:** self-run memtier_benchmark on one AWS c7i.16xlarge (64 cores): 9.07M ops/s at 160 connections, pipeline 30, 256B values, 1:1 SET:GET vs DragonflyDB 5.43M (1.7x) and Redis 7.0 2.03M (4.5x), p50 0.479ms vs Redis 2.383ms ([methodology](https://github.com/redistill-io/redistill/blob/main/docs/BENCHMARKS.md), raw memtier output checked into the repo). **Measured by:** author. **Type:** measured. **Arch:** `async-native`, `sharding`, `batching`.
- [polyxor](https://github.com/orlp/polyxor) - PolyXOR128, a keyed 128-bit universal hash for stream integrity with its collision bound machine-checked in Lean. **Blazing:** 126 GB/s single-thread at 16 MiB on a Ryzen 9950X (best of five 0.1 s runs, `target-cpu=native`, [CSV data](https://raw.githubusercontent.com/orlp/polyxor/master/assets/ryzen-9950x.csv)) - ~1.2x vs XXH3-128 (103 GB/s) and ~9x vs BLAKE3 (13.6 GB/s) in the same harness. **Measured by:** author. **Type:** measured. **Arch:** `simd`, `runtime-dispatch`, `proof-carrying-performance`.
